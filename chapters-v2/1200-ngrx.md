# 12. State Management with NgRx Signal Store [8h]

## Introduction

Once your app grows past "a couple of components call a couple of services", you need **state management**. NgRx is the dominant option in the Angular ecosystem. Historically, NgRx meant *actions / reducers / selectors / effects* (Redux-style). Angular 22's recommended approach is **`@ngrx/signals` Signal Store** — a far simpler API that composes naturally with signals.

This chapter uses **Signal Store** as the primary approach. The traditional Redux-style NgRx is covered as optional material at the end of this chapter, and in [Opt 2 — Normalized NgRx](opt-200-normalized-ngrx.md).

> **Note:** Talk to your mentor about this step. Don't get stuck alone.
> **Note:** State management is usually a medium-to-large project concern — we use it here to teach the fundamentals.

## Goal

### Theory

By the end of this chapter you should be able to explain:

- What state management solves and why the Online Shop benefits from it.
- The core Signal Store primitives:
  - `signalStore` — defines a store.
  - `withState` — the state shape.
  - `withComputed` — derived state.
  - `withMethods` — mutations and async operations.
  - `withHooks` — `onInit`, `onDestroy`.
- Why Signal Store state is exposed as signals, and how that plays with components.
- How to compose multiple stores (per feature) instead of one god-store.
- Where to connect a store to an HTTP service via `rxMethod` or plain async methods.
- Conceptually, what actions / reducers / selectors / effects were in classical NgRx.

### Practice

Add state management to the Online Shop using `@ngrx/signals`.

> `npm install @ngrx/signals`
>
> Create a `ProductsStore` with:
> - `withState({ products: [] as Product[], loading: false, selectedId: null as string | null })`
> - `withComputed` for a `selectedProduct()` derived from `products` and `selectedId`.
> - `withMethods` for `loadAll()`, `loadOne(id)`, `remove(id)`, `select(id)` — each delegating to `ProductsService`.
> - `withHooks({ onInit })` to kick off `loadAll()` on store init.
>
> Create a `ShoppingCartStore` with items, totals (`withComputed`), and `addItem / removeItem / changeQty / checkout` methods.
>
> Create a `UserStore` with current user and a method to call `/api/auth/profile`.
>
> Dispatch store methods / read store signals **only from container ("smart") components**. Keep presentational components dumb.

#### Rules

- Default to **Signal Store** throughout. Only reach for classical NgRx if a specific chapter / exercise asks.
- Loading flags live in state; show spinners in presentational components bound to them.

## Testing

> Test your `ProductsStore`:
>
> - Create the store in a `TestBed` with a stub `ProductsService`.
> - Call `loadAll()` and assert state transitions (`loading: true` → populated `products`, `loading: false`).
> - Call `select(id)` and assert `selectedProduct()` returns the matching product.
> - Call `remove(id)` and assert the item is gone from `products` state.

### Optional: Classical NgRx Store (actions / reducers / selectors / effects)

Real-world codebases you will join often still use **classical NgRx**: a global `Store`, actions, reducers, selectors, and effects. Read these to recognize the shape — they're the *legacy* form of state management, analogous to the decorator-era conventions in [Chapter 13](1300-legacy-angular-conventions.md).

- [NgRx Store — reducers & actions](https://ngrx.io/guide/store)
- [NgRx Effects](https://ngrx.io/guide/effects)
- [NgRx docs](https://ngrx.io/docs)

Use the modern creators:

```ts
// Action
export const increment = createAction('[Counter Component] Increment');

// Reducer
export const counterReducer = createReducer(
  initialState,
  on(increment, (state) => state + 1),
);

// Selector
export const selectCount = createSelector(
  (state: AppState) => state.counter,
  (counter) => counter,
);
```
